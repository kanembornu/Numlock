# Dashboard Consumer Inventory

## Scope and conclusion

This Sprint 5.15 Package 001 inventory is a repository-static audit of the public `getDashboardData(filter, customStart, customEnd)` response before any API projection or payload reduction. The response is assembled in [`90.Dashboard.Service.js`](../90.Dashboard.Service.js), called by the production browser through `google.script.run` in [`190.View.Index.html`](../190.View.Index.html), and covered by response-contract tests in [`96.Tests.Cases.js`](../96.Tests.Cases.js). No response, production source, permission, spreadsheet read, or deployment state changed.

API projection is **not ready for implementation**. The repository proves six fields are not directly rendered by the current frontend, but it cannot prove that deployed, editor-run, copied, bookmarked, or otherwise external consumers do not rely on the complete public response. A later projection proposal therefore needs consumer discovery outside this repository, an explicit permission model, an additive opt-in request contract, compatibility tests, payload measurements, and a rollback plan.

## Ownership, permission, and rollback constraints

- **Response owner:** `90.Dashboard.Service.js` owns the public global, one spreadsheet read/process path, filter resolution, response composition, and the seven-field recent-transaction projection. Analytics and intelligence builders own values placed into that response; they do not own browser authorization.
- **Frontend owner:** `190.View.Index.html` owns the only repository-confirmed production call, rendering, print, CSV, and bounded drill-down behavior.
- **Test owner:** `92.Tests.Fixtures.js`, `94.Tests.Assertions.js`, `96.Tests.Cases.js`, and `98.Tests.Runner.js` own deterministic shapes, required-field checks, frontend source contracts, and the parameterless production smoke call.
- **Permission boundary:** repository source shows one web-app call surface and no per-field scopes, role checks, caller identity checks, or separate DTOs. A smaller payload would reduce transferred data but would not itself create authorization. The actual deployment access policy and consumers must be verified outside Git.
- **Rollback constraint:** because external usage is unknown, a future implementation must keep the current full response as the default, make any projection additive and opt-in, preserve parameterless `currentYear` behavior, and support immediate rollback to the last known full-response deployment. Removing fields from the default response is not a safe first step.

## Unknowns and blockers

- Git search cannot enumerate callers in deployed browser sessions, copied Apps Script projects, Apps Script API clients, browser automation, integrations, or private scripts.
- Repository evidence does not expose deployment access settings, execution identity, access logs, telemetry, or stakeholder ownership. Therefore it cannot establish who can call the function or whether field-level privacy expectations differ by caller.
- The six non-rendered fields are only projection candidates. Their full-contract tests and unknown external dependency make direct removal unsafe.
- The sparse test's 37-entry `requiredProperties` list covers the complete current top-level response and separately requires `dateFilter.filter`, `startDate`, `endDate`, `label`, and `rowCount`.
- No representative serialized payload size, field-size distribution, network timing, or client parse/render trace was measured in this documentation package. Benefit is therefore unquantified.
- No approved projection selector, response version, deprecation window, compatibility fallback, or external-consumer migration process exists.

## Readiness recommendation

Do not reduce or change the default payload. The next safe step is a separate discovery/design package that verifies deployment configuration and available access evidence, identifies stakeholders and non-repository callers, measures representative payloads, and proposes an additive versioned or opt-in projection. Only then should the six current non-rendered fields be evaluated against measured benefit. Any proposal must preserve the full default response until all known consumers migrate and must treat `recentTransactions` as High-sensitivity transaction data rather than a general-purpose detail API.
